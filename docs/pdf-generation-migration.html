P-05 — Replacing ImageMagick for PNG→PDF

Why the scan pipeline no longer shells out to ImageMagick, what replaced it, and what was verified.

The Problem

The scan service converts scanned PNG pages into PDFs. It used to do this by shelling out to ImageMagick's convert/magick CLI via Node's exec(). Two issues made this a recurring, expected failure mode rather than an edge case:

  • Blocked by default. ImageMagick ships a policy.xml security policy that, on Ubuntu/Debian, blocks PDF read/write out of the box (rights="none" pattern="PDF"). Every scan on a fresh install failed with an "not authorized" error until someone manually edited /etc/ImageMagick-6/policy.xml. This was common enough that handleScanError() in scanService.js had a dedicated branch just to detect it and print the fix.
  • Slow. Spawning a CLI process per page adds process-launch and encode overhead — roughly 2-4 seconds per page. A 10-page scan added 20-40 seconds just for PDF assembly.

Where It Showed Up in Code

All of it lived in one file: src/services/scanService.js.

FunctionRole
combinePagesToPdf()Merged multiple scanned PNGs into one PDF (multi-page sessions, ADF "merged" mode)
convertPngToPdf()Converted a single PNG into its own PDF (ADF "separate" mode)
executeScan()Legacy single-shot /api/scan path — called ImageMagick directly via spawnAsync
checkPageDimensions()Diagnostic-only geometry check, shelled out to ImageMagick's identify
handleScanError()Detected the policy.xml failure and ImageMagick "not found" errors to produce a readable message
detectImageMagick(), IM_COMMANDModule-load-time probe to pick convert vs magick depending on installed version

Options Considered

Rejected

img2pdf (Python CLI)

Solves the policy.xml problem — no ImageMagick involved — and is fast (wraps images into a PDF without re-encoding). But it's a Python tool: it would require installing Python/pip on every host running this service. This team doesn't use Python anywhere else in the stack, so trading one CLI dependency (ImageMagick) for another (Python + pip + img2pdf) wasn't worth it.

Chosen

sharp + pdf-lib (Node)

Both are plain npm packages, installed with npm install — no OS packages, no external CLI, no Python. sharp ships prebuilt native binaries for Linux/macOS/Windows (nothing to compile). pdf-lib is pure JavaScript. Both run in-process, eliminating the per-page CLI spawn cost entirely.

What Changed

package.json

Added two dependencies:

"pdf-lib": "^1.17.1",
"sharp": "^0.33.5"

scanService.js

  • Removed IM_COMMAND, detectImageMagick(), imgToPdfCmd(), and buildImgToPdfArgs() entirely — there's no ImageMagick binary to detect or shell out to anymore.
  • Added pngToJpegBuffer(pngPath) — uses sharp to recompress a scanned PNG to JPEG at the same quality ImageMagick used to apply (SCAN_QUALITY, default 82).
  • Added embedPageImage(pdfDoc, pngPath) — embeds one JPEG-compressed page into a pdf-lib PDFDocument, sized to fill the page.
  • combinePagesToPdf() and convertPngToPdf() rewritten to build a PDFDocument in-process and write it to disk with fs.writeFileSync — same function signatures, same output contract, no subprocess.
  • executeScan()'s legacy single-shot path now calls the same convertPngToPdf logic instead of spawnAsync(IM_COMMAND, buildImgToPdfArgs(...)).
  • checkPageDimensions() now reads width/height via sharp(path).metadata() instead of shelling out to identify.
  • handleScanError() — removed the policy.xml branch and the ImageMagick-specific wording in the "not found" branch, since that failure mode no longer exists for this service.

README.md

  • Architecture diagram updated: PNG → ImageMagick → PDF → PNG → sharp/pdf-lib → PDF.
  • Removed imagemagick from the Linux/macOS install instructions and dropped the "convert: not found" troubleshooting entry.
  • Added a "PDF Generation: Why No ImageMagick" section with the same problem/options/solution summary as this page, for anyone reading the README who wonders why there's no ImageMagick install step.
Nothing downstream changed. Routes (scanSession.routes.js, docs.routes.js), the ADF job manager (autoScanJobManager.js), and the frontend all just expect a valid PDF file to exist at a given path — none of them care how the bytes were produced. That's what made this a safe, contained, drop-in swap.

Verification

  1. npm install in scaning-nodejs/ to pull in sharp and pdf-lib.
  2. Single-shot scan (GET /api/scan) → confirmed executeScan produces a valid, openable PDF.
  3. Multi-page manual scan session (POST /api/scan/complete/:sessionId) → confirmed combinePagesToPdf merges multiple pages in order into one valid PDF.
  4. ADF auto-scan job, both "separate" and "merged" output modes → confirmed convertPngToPdf/combinePagesToPdf are invoked correctly and jobs finalize with valid filePaths.
  5. Compared output PDF file sizes against prior ImageMagick-produced PDFs for the same source pages — comparable, given matching JPEG quality.
  6. Fetched a produced PDF via GET /api/docs/:examCode/:filename and confirmed it renders correctly in the browser.
  7. Confirmed no remaining references to convert/magick/IM_COMMAND/policy.xml in scanService.js.
